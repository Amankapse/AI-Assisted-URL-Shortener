- `P-013`: Blocker was missing `flyway-database-postgresql`. Root cause was PostgreSQL support being separated from `flyway-core` in Flyway 11. Approved correction was adding `org.flywaydb:flyway-database-postgresql` as a production/runtime dependency managed by Spring Boot while retaining `flyway-core`. Validation confirmed both modules resolved to `11.7.2`, Testcontainers PostgreSQL started, Flyway applied migrations, Hibernate validation succeeded, and the Maven build passed.
- `P-015`: After Flyway started, failures were treated as migration/schema/mapping/test defects. Fixed V2/Hibernate digest type mismatch, refresh-token reuse transaction rollback, invalid-refresh cookie clearing, and test cleanup order for the V2 FK.
- `P-016`: After Flyway started, failures were treated as migration/schema/mapping/test defects. Fixed physical URL deletion conflicting with retained click events by adding soft deletion in V3, and fixed test isolation/order issues caused by analytics FKs and async persistence.
- `P-017`: No new Flyway blocker or migration was required. A readiness-policy defect was found when Redis health affected aggregate health; fixed by excluding Redis from Actuator health because Redis is an optimization and PostgreSQL remains the source of truth.
- `P-019`: No application blocker was found. Documentation verification found one artifact defect: the k6 URL creation script did not match the current create DTO because `expiresAt` was missing. The script was corrected as documentation/test-artifact alignment, not product behavior.
- `P-020`: No dependency blocker was introduced. The approved migration was limited to V4 `blocked`; broader lifecycle enums, persisted quota tables, and distributed infrastructure were rejected or deferred to architecture docs.
- `P-021`: No deployment dependency blocker was found. Render readiness required profile/config and Docker runtime changes only; Neon PostgreSQL and Render Key Value are configured through environment variables with no committed secrets.
- `P-021 Render deploy`: Render failed with `no main manifest attribute` because Maven produced a normal JAR. Root cause was that the project imports Spring Boot dependency management but does not use `spring-boot-starter-parent`, so `spring-boot:repackage` was not automatically bound. Approved correction was binding the `repackage` goal in the existing Spring Boot Maven plugin; no dependency or application behavior change was required.
- `P-022`: No dependency blocker was introduced. The approved V5 migration added idempotency storage only. The implementation kept `Idempotency-Key` optional for backward compatibility and left workspace/RBAC migration for the next reviewed stage.
- `P-023`: No dependency blocker was introduced. Stage 4 required an additive V6 migration. Implementation defects found during validation were treated as schema/API/test defects after Flyway startup: explicit controller path-variable names were added, and test fixtures were corrected to reuse default workspaces.

Implementation defects found during validation were treated as API/query/test defects after Flyway startup: explicit audit controller parameter names were added, and nullable JPQL filters were replaced with dynamic JPA specifications for PostgreSQL compatibility.
- `P-025`: No production dependency blocker was introduced. Stage 6 required additive V8 API-key storage and audit-constraint expansion only. Implementation review corrected API-key filter registration and filter-local rate-limit error handling; broader API-management features remain out of scope.
